## 🌟 Grand Vision (Итоговая цель)

## 🟢 STAGE 5: Meta Time Scaling (Global Time Warp) ✅ COMPLETED
**Суть:** Глобальный ползунок "мета-масштабирования времени", который сжимает/растягивает темп полного цикла.

- [x] Time Warp Scale UI (0.5x - 2.0x) в SettingsScreen
- [x] _getScaledPhaseDuration() с clamp-валидацией и fallback 1.0
- [x] Guard _phaseCompleted от повторного триггера перехода фазы
- [x] Пересчёт окончания текущей фазы при изменении ползунка **во время RUNNING** (без рестарта, с сохранением доли пройденного времени; поле `currentPhaseBaseSeconds`)
- [x] Явная валидация NaN/Infinity/вне диапазона → fallback 1.0 в `setTimeWarpScale`
- [x] Применение масштаба ко всем фазам: THINKING, PREP, STRIKE, RECOVERY
- [x] Сохранение/восстановление timeWarpScale из SharedPreferences

**Статус:** Завершено в рамках Upgrade Pipeline v1.1.

**Бизнес-ценность:** Качество выполнения за счет управляемого ритма: низкий масштаб = разгон (быстрый прогон фаз), высокий масштаб = глубокое погружение (растяжение фаз), при этом переходы остаются корректными и последовательность фаз не ломается.

**Что делаем:**
- **ТОЛЬКО** добавить глобальный ползунок, который преобразует длительности цикла/фаз по прогрессивному правилу: низкий масштаб сжимает весь цикл, высокий — растягивает; применение масштаба устроено так, чтобы исключить зависание в отдельной фазе (контролируемый темп, не случайность).

**ЧЕГО МЫ НЕ ДЕЛАЕМ:** авторизация, платежи, профили, новые цели/оверлеи — **всё вырезано** (только управление временем цикла).

## 🟢 STAGE 6: Deep Flow Inertia Controller (Auto after Phase 3) [x] ✅ COMPLETED
**Суть:** После фазы 3 (“Уничтожай”) приложение автоматически переводит пользователя в режим **INERTIA** без каких-либо дополнительных запросов инерции/отдыха.

---



**Правила INERTIA:**
- **Автовход:** сразу после завершения фазы 3.
- **Pulse (мягкий звуковой сигнал):** уведомляет пользователя, что он всё ещё находится в режиме инерции.
  - Интервал **рандомный 2–3 минуты**
  - Тот же тип сигнала, но **не сильно отвлекающий**
- **UI режима:** только одна кнопка **EXIT**.
- **Выход из INERTIA:**
  - При нажатии **EXIT** система **выходит из цикла инерции** и запускает стандартный переход в **режим отдыха**.
  - Дальше поведение как и раньше: отдых → в цель → после цели дальнейшая логика как в текущей системе (либо цель создана, либо нет).
- **Лимит бездействия:** в INERTIA без действия пользователя можно находиться **только 3 цикла**.
- **Проверка после 3 цикла:**
  - появляется вопрос (оверлей): **“Всё ещё в инерции?” / “MAX FLOW REACHED. CONTINUE?”**
  - у пользователя **30 секунд**, чтобы ответить **YES**
  - если ответа **нет** → **автоматический выход в отдых** и далее по обычной логике.

**Фактически реализовано (вышло за рамки черновика):**
- **Автовход в INERTIA** сразу после STRIKE через `_enterInertiaMode()` (без UI-выбора). Guard от повторного входа: `_lastInertiaPhaseTransitionId` + `_currentStrikeTransitionId` + проверка `_isInertiaMode`.
- **Dead Man's Switch после STRIKE удалён** (метод `_startDeadManSwitch` убран) — вместо него авто-INERTIA.
- **Pulse-планировщик:** рандом 2–3 мин, ровно один pulse на окно (перепланировка deadline), остановка при выходе, пересчёт после рестарта без дублей.
- **Pulse масштабируется `timeWarpScale`** (cross-upgrade V1.1×V1.2): интервал 2–3 мин умножается на масштаб; при движении ползунка во время INERTIA отложенный pulse пересчитывается.
- **UI Lock:** в INERTIA только кнопка **EXIT** (бывш. «ЗАВЕРШИТЬ ИНЕРЦИЮ»); ветвь ИНЕРЦИЯ/ОТДЫХ скрыта.
- **MAX FLOW (на 3-м цикле):** оверлей «MAX FLOW REACHED. CONTINUE?» + звук `beep.mp3` ровно один раз; кнопки **YES** (продолжить, счётчик сбрасывается) и **NO** (выход в отдых); авто-выход в отдых по таймауту 30с (`_autoExitMaxFlow`). Счётчик «Цикл X/3» виден в уведомлении.
- **Persistence:** 5 ключей SharedPreferences для устойчивости INERTIA (`inertiaCycleCount`, `inertiaNextPulseAtMillis`, `inertiaPendingMaxFlowConfirmUntilMillis`, `isInertiaConfirmShown`, `lastInertiaPhaseTransitionId`) + `currentPhaseBaseSeconds` (V1.1).
- **🛑 Deviation:** авто-вход в INERTIA теперь **без проверки Premium** (Paywall Stage 11 «Инерция только для Premium» не применяется в V1.2). См. TECH_SPEC.md → As-Built Deviations V1.1/V1.2.

**Статус:** Завершено в рамках Upgrade Pipeline v1.2.

## 🟢 STAGE 7: User Scheduler & AUTO-ENGAGE PROTOCOL (THE HIT-LIST) [x] ✅ COMPLETED
**Суть:** Пользователь планирует время “включить работу” — а приложение само делает авто-старт (вместо ручного нажатия пользователем). Ежедневно повторяется, чтобы не забывал “байпас режим хищника”.

**Статус:** Завершено в рамках Upgrade Pipeline v1.3 (PRD/TECH_SPEC → Version 1.3 - Auto-Start Scheduler «THE HIT-LIST»).

**Фактически реализовано (вышло за рамки/отклонилось от черновика Stage 7):**
- **Экран THE HIT-LIST** (`HitListScreen`): список слотов (до 10), переключатель `ВКЛЮЧЁН` на каждый слот, выбор HH:mm через ползунки (ЧАС 0–23 / МИН 0–59), добавление/удаление; вход из `SettingsScreen`. Расписание активно, если включён хотя бы один слот.
- **Авто-старт по расписанию:** `HitListProvider.processScheduledTriggers()` каждые 15с сверяет включённые слоты с текущим `HH:mm` и вызывает `TimerProvider.autoStartFromScheduler(...)`, переводя систему в фазу 0 + `needsTargetConfirmation=true` (оверлей «ЦЕЛЬ НАЙДЕНА?» как при обычном старте).
- **Защита от конфликтов:** если `timerProvider.isRunning == true` — авто-старт no-op; winner при совпадении времени — слот с минимальным `slotOrdinal`; idempotent-окно `yyyy-MM-dd|HH:mm` исключает дубли в одну минуту (persisted `hitListLastExecutedMinuteWindow`).
- **🛑 Deviation 1 (звук):** по фидбеку добавлен выделенный sustained-сигнал `AudioService.playScheduleAlarm()` — зацикленный `beep.mp3` ≥ 30 секунд (вместо «тихого» старта из черновика §2). Останавливается на СБРОС/подтверждении цели.
- **🛑 Deviation 2 (механизм будильника):** AC5 черновика («права как у будильника», авто-старт после выгрузки/ребута) **НЕ выполнен** — реализован in-app poll 15с поверх foreground service, без Android `AlarmManager`/boot-receiver. Авто-старт срабатывает только пока жив процесс.
- **🛑 Deviation 3 (однократность):** флажок «Repeat daily = однократно» из черновика §4 **не реализован** — все включённые слоты повторяются ежедневно, переключателя однократности нет.

См. TECH_SPEC.md → As-Built Deviations V1.3 (Auto-Start Scheduler «THE HIT-LIST»).

### 1) UI / Экран “THE HIT-LIST”
- Новый отдельный экран планировщика:
  - список/карточки “MISSION TIMES” (например: 18:00, 20:00, 21:00)
  - кнопка добавления миссии: **ADD MISSION**
  - флажок **Repeat daily** (повторять каждый день) — для каждой миссии/слота или для всего расписания (как решим в реализации)
  - флажок **ENABLED** (расписание активировано/выключено)
- На каждой карточке:
  - выбранное время
  - удаление/отключение времени (опционально)

### 2) Контракт AUTO-ENGAGE (поведение по таймеру)
В выбранное время приложение должно:
- ИНИЦИИРОВАТЬ запуск цикла/старт автоматически (без ручного нажатия пользователем):
  - перевод в состояние **RUNNING/ENGAGE** (логика существующего таймера, без изменения фаз)
- НИКАКИХ дополнительных сигналов/уведомлений пользователю не требуется:
  - никаких “beep/месседжей” и отдельного UI-сообщения ради уведомления — только запуск таймера
- Приложение должно иметь права уровня **как у будильника** (разрешения и механизмы background/auto-start):
  - чтобы авто-старт происходил даже если приложение было выключено/в фоне, насколько это поддерживает платформа

### 3) Сценарий целеполагания (60 секунд)
- После авто-старта (в логике текущей фазы THINKING / Target Confirmation):
  - пользователь получает **60 секунд** на формулировку цели
  - если цель не выбрана — действовать по уже реализованной в Stage 0 механике “циклирования” в рамках ожидания выбора

### 4) Повторение по флажку
- Если флажок **Repeat daily** включён, то слот времени повторяется **каждый день**.
- Если флажок **Repeat daily** выключен, то автозапуск выполняется **однократно**.
- Дедупликация автозапуска:
  - не запускать повторно один и тот же слот времени в рамках “уже было” (guard по `lastFiredDate`/`lastFiredTriggerId` в зависимости от реализации).

### 5) Технологическая модель (устойчивость к перезапускам)
- Использовать абсолютные timestamp’ы (как в TECH_SPEC):
  - `nextTriggerAtMillis` / “deadline” следующего события
- Guard от дублей:
  - хранить `lastFiredDate` (YYYY-MM-DD) или `lastFiredTriggerId`
- При рестарте приложения:
  - пересчитать “следующее срабатывание” и продолжить планирование.

### 6) Persistence / SharedPreferences (ключи — концепт)
Ожидаемые ключи (точные названия синхронизируем позже с реализацией):
- `schedulerEnabled` (bool)
- `scheduledTimes` (массив строк типа “HH:mm” или чисел минут после полуночи)
- `nextTriggerAtMillis` (int?)
- `lastFiredDate` (string?)
- `lastFiredTriggerId` (int? / string?) — чтобы исключить двойной автозапуск

### 7) Acceptance Criteria
- **AC1:** пользователь добавляет время и включает ENABLED
- **AC2:** в заданное время приложение автоматически включает запуск (без ручного нажатия)
- **AC3:** если включён **Repeat daily**, автозапуск повторяется каждый день; если выключен — срабатывает один раз
- **AC4:** при перезапуске приложения авто-старты не дублируются
- **AC5:** приложение имеет необходимые права “как у будильника”, чтобы авто-старт происходил в требуемых background-сценариях

**Бизнес-ценность:** превращает “я начну когда-нибудь” в “у меня назначена охота” — лень теряет точку входа, потому что старт приходит сам.
